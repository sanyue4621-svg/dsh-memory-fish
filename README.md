# dsh-fish-memory

**Live memory for DeepSeek Harness — survives compaction.**

DSH 的自动压缩，会把前面一大段对话交给模型写成摘要，只留最近一点原文。

摘要留下的是「做了什么」，丢掉的是「说过什么」——

> 「她说她不介意」和「她说『我不介意』的时候停了两秒」是两回事。
> 前者是摘要能留的，后者要靠原文。

这个插件在压缩之外另存一份原始记忆：每轮只往回带一小段，让压缩之后的人还认得出对面是谁。

---

## 一、它解决什么问题

会话一压缩就失忆。

不是「忘记你叫什么」那种失忆——模型能从摘要里知道「我们在讨论压缩配置」。丢掉的是更细的东西：当时怎么说的、什么语气、为什么这么决定、那天情绪是什么样。

**这三个月的对话压成一段摘要，等于活成了一个人设。**

所以这里做的不是「提高摘要质量」，是**在上下文窗口之外留一份原文**，压缩管压缩，记忆管记忆。

## 二、设计：按天存，不按条筛

这是整个插件唯一值得讲的设计决定。

主流做法是「存 N 条记忆，每轮按相关度挑 3 条注入」。问题是：

- 相关度是怎么算的？用户永远看不出来
- 为什么挑这条不挑那条？没人知道
- 挑错的代价是：本来该在的东西不在，而你在上下文里看不到「它不在」

**这里是另一条路：按天存，按时间取。**

- 每天的记忆是一组（那天说过的话、发生的事、情绪），不是散落的 N 条
- 注入时先看「最近几天」的，再往远的翻
- 时间上连续的几条，本身就是上下文；单条再相关，孤立着也没用

**说得直接一点：**

> 「昨天你说了三句话，今天你说了两句」——这个形状本身就是信息。
> 「这两条记忆相关度 0.83」——这个是算法。

代价是：它不擅长「从三个月前精确召回某一条」。这件事更该由搜索（grep / FTS）做，不该由注入做。

## 三、装

```sh
# 装进 profile（跟其他 DSH 插件一样）
dsh plugin --profile desktop add dsh-fish-memory
```

或者手动：把本仓库放进 `<profile>/local-plugins/`，在 profile 的 `package.json` 里加依赖和 bundle，重启 DSH。

第一次启动会自己在数据目录建表。

管理页：`http://127.0.0.1:<端口>/fish-memory/admin`

## 四、数据存在哪

**默认：`<插件目录>/data/memory.db`**（一个 SQLite 文件）

想换地方，设环境变量：

```sh
FISH_MEMORY_HOME=D:\my-memory
```

目录结构：

```
data/
  memory.db          # 主库（三张表：memories / fts / meta）
  seen.json          # 每会话已注入过的 id（上限 300 条/会话）
  probe-state.json   # 可选：外部工具写的「上次压缩时间」，注入分界靠它（见第八节）
  logs/
    plugin.log       # 运行日志
    injections.jsonl # 每次注入的明细（管理页读它）
```

**三张表：**

| 表 | 干什么 |
|---|---|
| `memories` | 记忆本体：text / feel / mood / heat / status / lib |
| `fts` | 二元词倒排，给关键词搜用 |
| `meta` | 零碎状态：最近情绪、会话→库的绑定 |

`status` 三态：`current`（活着）/ `forgotten`（遗忘区，还能捞回来）/ `doomed`（待删）。

`heat` 是「温度」0~1：被提起就升，久不想就降。降到线下进遗忘区——**不是删除**。

## 五、怎么备份

**整个 `data/` 目录拷走就是备份。**

```powershell
# Windows
Copy-Item -Recurse "$env:USERPROFILE\.dsh\profiles\desktop\local-plugins\dsh-fish-memory\data" `
                    "D:\backup\fish-memory-$(Get-Date -Format yyyyMMdd)"
```

```sh
# macOS / Linux
cp -r ./data ~/backup/fish-memory-$(date +%Y%m%d)
```

想跑成定时任务，加一条计划任务/`cron` 就行。**建议每天一次**——记忆是累积的，丢一天就少一天。

**注意**：SQLite 是单文件，直接拷是安全的（没有正在写入时）。如果担心，先停 DSH 再拷。

## 六、怎么迁移

**换机器 / 换目录：**

1. 停 DSH
2. 把旧机器的 `data/` 整个拷到新机器
3. 要么放回默认位置（插件目录下），要么设 `FISH_MEMORY_HOME` 指过去
4. 起 DSH

**只迁移一部分库：**

```sh
# 把 scratch 库的条目导出成 SQL（或者用 sqlite3 .dump）
sqlite3 memory.db ".dump memories" | grep scratch > scratch.sql
```

或者在管理页按库筛选，手动复制文本。

**从旧版同类插件迁过来？** 表结构一样，直接拷 `memory.db` 就能用。库名要改的话：

```sql
update memories set lib = 'default' where lib = 'main';
update memories set lib = 'scratch' where lib = 'tech';
```

## 七、库怎么分

每条记忆属于一个库（`lib`），翻记忆时按库过滤，不串门。

- **`default`** — 主库
- **`scratch`** — 试验库。**没绑定库的会话默认走这里**，免得把主库弄脏

给会话绑库：

```sql
insert or replace into meta (k, v) values ('lib:<会话 id>', 'default');
```

管理页也能改单条的库。

## 八、注入是怎么收的

宁可不塞，也别塞噪音。

### 分界：压缩之后说过的不塞

这是这个插件最关键的一条判断。

**为什么：**

- **压缩之后**说过的话，一定还在上下文里 —— 再塞一遍是重复
- **压缩之前**的事，原文已经被摘要换掉了，只剩梗概 —— 细节没了，那部分才该补

摘要留得住「做过什么」，留不住「怎么说过的」。所以分界不能按时间算，要按**上次压缩的那一刻**算：

- 条目时间 **早于** 上次压缩 → 塞（那部分上下文里已经没了）
- 条目时间 **晚于** 上次压缩 → 不塞（还在上下文里）

> 为什么不用「24 小时内不塞」直接判断：压缩不是按天发生的。一天压三次和三天不压，用同一个时间窗都是错的。

那条线从哪来？插件读数据目录里的 `probe-state.json`，取 `上次压缩时间` 字段（毫秒时间戳）。这个文件可以由任何知道「压缩什么时候发生」的工具写 —— 比如一个挂在压缩事件上的探针。

**没有这个文件、没有这个字段、或值是 0 → 退回按时间算：一天内记下的不塞。**

### 其他三条

1. **一轮最多一条**（相关 1，情绪 0，随手 0）
2. **门槛 0.62** —— 热但不贴题的别硬塞
3. **塞过的 id 不再塞** —— `seen.json` 记着，每会话上限 300 条

拼出来的样子：

```
【记得的事】
- 昨天说想把那个视频投稿，但是怕没人看（当时：有点怂）

（不确定就说个大概，留个印象；别硬提）
```

**注入的文本里不带任何来源标记**——那些是给管理页看的，塞进上下文就是噪音。

## 九、写入为什么不在插件里

插件只管读。写入（`记一条`）由插件里那个「每五轮压一次」的逻辑调存储层完成，但**存储层本身不依赖插件**——`记忆.mjs` 可以单独 `import` 用。

好处：

- 插件挂了不影响存
- 能写脚本批量导入/清理
- 迁移、备份都只碰一个文件

## 十、已知限制

- **关键词是二元切词**，不是分词器。中文够用，英文一般
- **不擅长精确召回**：三个月前的某一条，靠注入翻不到，得搜索
- **每五轮一次模型调用**（压记忆），会花钱
- **`seen.json` 没有过期清理**：会话多了文件会变大（每会话 300 条上限）
